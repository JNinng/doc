# 知识沉淀（local_knowledge/）

将探索代码或会话讨论中获得的可复用理解，沉淀为 `local_knowledge/` 下的自包含知识文档。

## 判断沉淀什么

沉淀（跨会话可复用、项目文档未覆盖的理解）：

• 某个机制/子系统的端到端解释：数据从哪来、落到哪、如何取用

• 代码索引：文件 + 符号 + 行为对照表

• 已知坑：必须有真实出处（哪里踩过）

• 多方案对比结论（表格呈现取舍）

• 对项目既有文档的增量理解——文档已详述的内容只放链接，不复制正文


不沉淀：

• 过程记录、调试叙事（归 Git/Issue/CHANGELOG）

• 一次性结论：只对当前任务有效、无复用价值

• 未经验证的猜测


## 自适应工作流

沉淀请求有两种常见形态，走同一条流程，差异只在素材起点：

• 点题式：「沉淀消息来源」——主题明确，素材不全。从主题出发，查已有知识与文档，再探索代码补齐。

• 总结式：「总结上面提到的事件机制」——主题和素材都在当前会话里。从会话已确认的结论出发，补齐代码引用。


统一流程：

1. 定主题：用户点名，或从会话内容归纳；与用户确认归纳结果（仅当会话内有多个候选主题或目标不清晰时）。
2. 查已有：先查 `local_knowledge/` 是否已有覆盖——主题重叠时合并入已有文件，不新建。
3. 收素材：会话中已确认的结论 + 项目既有文档 + 相关代码；两者取并集，文档已有的只留增量。
4. 验证：行为性结论必须对照当前代码核实；会话中未验证的补验证，验证不了的不沉淀。
5. 成文：按文件规范写入或合并，并同步更新 [README.md](README.md) 索引表；会话中发现既有知识文件失实时，直接修正并写明正确行为，不留"曾经错了"的过程叙述。

## 文件规范

• 命名：跟随目录内既有文件的风格（前缀、分隔符保持一致）；目录为空时用 `<主题>.md`，kebab-case。

• 结构：

  1. `# 标题` + 简述定位（引言块说明本文覆盖什么）
  2. 按数据流/逻辑分层分节（来源 → 落盘 → 获取路径 → 对比 → 代码索引）
  3. 结论用表格、代码块、要点列表呈现；关键代码段直接摘录
  4. 结尾"相关代码索引"表：文件 → 内容
• 索引：`README.md` 是渐进式披露入口——每行一个文件，只写"文件链接 + 定位 + 覆盖主题"，读者据摘要决定是否打开正文；新增、合并、重命名、删除知识文件时同步更新。

• 引用：文件用相对路径 markdown 链接或 `path` 代码样式；行号会漂移，定位以"文件 + 符号名"为主、行号为辅。


## 质量标准

• 自包含：读者无需回翻会话或旧对话即可理解；不写"如上面讨论的"。

• 已验证：每个行为性结论对照当前代码核实；来自真实踩坑的坑要写出处。

• 单一事实归属：项目文档已有的只链接；knowledge/ 内同一事实只在一处详述，其他位置链接过去。

• 增量维护：新知识优先合并入已有文件的相关小节；仅当主题确实独立才新建文件。


## 与其他记录的关系

| 记录位置                     | 放什么                     |
| ---------------------------- | -------------------------- |
| `local_knowledge/`           | 可复用的机制理解与代码索引 |
| 项目文档（docs/、README）    | 产品文档与使用指南         |
| 决策记录（ADR、Agent Notes） | 架构决策理由               |
| 会话记忆                     | 过程性 TODO 与临时上下文   |

若沉淀内容实为决策理由，引导用户走项目的决策记录（ADR/Agent Notes）；若属于应写入项目文档的产品内容，写入对应文档，local_knowledge/ 只留索引。
